Scenario A scores loan applicants before funding. Scenario B monitors the funded book. Both are CatBoost models evaluated out-of-time, calibrated, thresholded on expected cost, and shipped as reproducible pipelines with drift monitoring.

Internal use
Frame: this is a results briefing, not a tutorial. Two models, one shared engine, honest limits.

Context

Lenders need calibrated default probabilities at two decision points

Decision 1: Approve or reject (before funding)

Every applicant needs a probability of default before money moves. A score that only ranks well is not enough: pricing, limits, and fair-lending review all need probabilities that mean what they say.

Decision 2: Monitor the funded book (after origination)

Once funded, pricing and loan-structure fields exist. The book needs re-scoring as vintages age, with drift detection when the world changes.

What this project delivers: two models answering those two questions, evaluated on genuinely unseen future loans, with every claim traceable to a committed report.
Situation
Keep it plain: ranking vs probability. Calibration is the business-critical property.

Architecture

Scenario A answers "should we fund this applicant?" Scenario B answers "how risky is this funded loan?"

Scenario A · application-time

Approve / reject

  • 14 features: bureau, demographic, derived (credit age, DTI, LTI)
  • Uses only what an applicant tells you and the bureau reports
  • Hard-blocks funding, repayment, and collection fields
  • OOT AUC 0.644 τ = 0.288

Scenario B · post-origination

Funded-book monitoring

  • 28 features: Scenario A set + grade, int_rate, installment, funded_amnt
  • Scoring entry point rejects payloads containing repayment/collection fields
  • Same shared engine (pipeline/core.py), separate feature contract
  • OOT AUC 0.669 τ = 0.282

Trust

Forbidden features are rejected by the pipeline itself, so analysts can't leak them by mistake

What never enters a model

  • Repayment outcomes: recoveries, out_prncp, total_pymnt, last_pymnt_*
  • Collection fields: collection_recovery_fee, pymnt_plan
  • Scenario A also excludes all funding/pricing fields

How it is enforced

  • FORBIDDEN_FEATURES lists live in each scenario's features.py
  • Scenario B scorer hard-rejects payloads containing blocked columns
  • pipeline/infer.py strips them per scenario when routing one record
  • Calibration and τ are chosen on validation; the OOT test set is touched once
This is the difference between a notebook that looks good and a model that survives production.

Robustness

Rolling-origin evaluation shows gradual drift, so a scheduled retraining cadence is sufficient

  • Refit on expanding window, score the next quarter: 16 windows per scenario
  • Expect OOT AUC ~0.64-0.67 on future vintages; the 2010 peak is not recoverable
  • Bad rates drift with Lending Club's book growth, which is what PSI monitoring is designed to catch
  • Full run < 5 min per scenario: cheap validation before promoting any retrained bundle

Uncertainty

Venn-Abers conformal intervals give each loan a defensible PD range for risk committees

How it works

  • Isotonic calibration fit twice on the 10,596-loan validation set, with the label forced to 0 and then to 1
  • Interval [min(p0,p1), max(p0,p1)] brackets a calibrated probability per loan
  • Wired into scoring: --intervals on score.py and infer.py
  • Distribution-free coverage guarantees under exchangeability

Why it matters

  • Near-threshold loans get visibly wider intervals → manual review queue
  • Risk committees see uncertainty, not false precision
  • Complements the bootstrap τ analysis: score-level and threshold-level uncertainty both quantified

Source: experiments/reports/conformal_coverage.md · src/conformal.py

Uncertainty
Novel-ish capability most credit shops don't have. Keep it brief; the technical audience will get it.

Monitoring

Every scoring batch emits a PSI drift report covering per-feature and score-distribution drift, with a verdict

What is monitored

  • Characteristic PSI per feature vs reference distribution
  • Score-distribution PSI: is the book's risk mix shifting?
  • Overall verdict: Stable / Moderate / Significant
  • Natural-sort bin ordering (audit fix) so drift localizes correctly

Why it matters now

  • Rolling evaluation proved drift is gradual , which is what PSI catches early
  • Triggers the scheduled retraining cadence before AUC degrades visibly
  • Regression test: shifted-feature fixture produces material PSI + non-stable verdict

Recommendation

Deploy Scenario A for approve/reject decisions and Scenario B for funded-book monitoring, starting with a pilot

Scenario A → origination

  • Score every applicant; τ = 0.288 decision boundary
  • SHAP waterfall per decline → adverse-action reasons
  • Venn-Abers interval flags borderline cases for review
  • Report PDs with the documented funding-conditional caveat

Scenario B → portfolio management

  • Re-score funded book on each reporting cycle
  • PSI report per batch → retraining trigger
  • Segment dashboards watch the three flagged groups
  • Hazard model available for horizon-specific EL questions
Both bundles reproduce with python -m pipeline.scenario_{a,b}.train; unified scoring via pipeline/infer.py.
Recommendation
Concrete deployment shape. Pilot, not big-bang: shadow mode alongside the existing process first.

Asks

Stakeholders must decide: how to handle reject-data bias, τ governance, and retraining cadence

1 · Reject-level data

Accept funded-conditional PDs with documented bounds (1.4-1.9×, oracle τ 0.12-0.18), or invest in collecting/scoring rejected applicants to close the gap.

2 · τ governance

Approve the expected-cost τ policy (C_FN ≈ 8.25M vs C_FP ≈ 2.7M IDR) and its review cadence. Statistical uncertainty is small; policy risk is not.

3 · Retraining cadence

Approve scheduled retraining (~semi-annual, PSI-triggered early). Rolling evaluation shows gradual drift, not abrupt breaks.

Asks
Each ask maps to a documented finding. Don't ask for blanket approval. Ask for three decisions.

Next steps

Three scoped next steps: reject data, live shadow validation, retraining automation

1 · Reject-level data collection

Highest-value gap: turns bounded bias into measured bias. Reject-inference module already accepts augmented files.
